# x402-signals — v0.1 (DRAFT)

A small, machine-readable convention for x402 services to declare
**fulfillment SLA**, **refund policy**, and **operational signals** so
that paying agents can reason about risk, wait, and recovery without
human intervention.

| Field | Value |
|---|---|
| **Status** | DRAFT |
| **Version** | 0.1 |
| **Editors** | x402station |
| **Pilot target** | ReloadPI (eSIM / topups / vouchers, x402 mainnet). The protocol-design questions that triggered this draft came from ReloadPI; manifest publication and spec-conformance work is upcoming. |
| **Audience** | x402 service operators, agent framework authors, facilitators |
| **License** | CC0 1.0 — public domain dedication |
| **Source of truth** | `v0.1.md` in [github.com/sF1nX/x402-signals](https://github.com/sF1nX/x402-signals) |

> **Why this exists.** x402 settles money in seconds. It does not yet say
> what an agent should expect when an upstream supplier is degraded, when
> fulfillment takes longer than the HTTP request, or when a paid call
> fails after settlement. This note proposes a minimal vocabulary so that
> honest operators can describe their behaviour, and agents can act on
> it, without each provider inventing a private convention.

---

## 1. Scope

### 1.1 In scope

- A canonical **state machine** covering the lifecycle of a paid x402
  call from challenge to terminal outcome, including refund.
- Three **machine-readable fields** that providers MAY publish in their
  `/.well-known/x402` document or as an x402 challenge extension:
  `fulfillment_policy`, `refund_policy`, `signals`.
- A small set of **terminal statuses** with strict semantics
  (`FULFILLED`, `FULFILLMENT_FAILED`, `REFUNDED`, `PARTIALLY_REFUNDED`,
  `REFUND_FAILED`).
- A reference shape for a **status endpoint** (Google LRO style) and a
  **refund endpoint** (Stripe / Adyen / Coinbase style).

### 1.2 Out of scope

- Webhook delivery semantics. Webhook retry windows are operator
  concerns, not protocol concerns. Where webhooks are referenced (§5),
  they are treated as a transport hint, not normative behaviour.
- Cross-chain settlement, non-USDC currencies, alternative facilitators.
  This note is asset- and facilitator-agnostic but written in the
  presence of the existing x402 envelope (`PAYMENT-REQUIRED`,
  `PAYMENT-SIGNATURE`, `PAYMENT-RESPONSE`, `extensions[bazaar]`).
- A registry of refund reason codes. Operators describe failure in
  free-form `reason` strings; future versions may standardise codes.
- Legal compliance, KYC/AML, fiat off-ramps. This is an engineering
  convention, not a regulatory framework.

### 1.3 Non-goals

- This document **does not** require any agent to consume these fields.
  Agents that ignore `x402-signals` continue to interoperate with
  providers that publish them.
- This document **does not** mandate refund policy. A provider MAY
  publish `refund_policy.type = "none"`. Agents are then free to refuse
  to pay, but the provider is not in violation of the spec.
- This document **does not** define a new wire envelope. It piggybacks
  on x402 (`/.well-known/x402` or challenge `extensions`) and ordinary
  HTTP for status/refund endpoints.

## 2. Terminology

The key words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, and
**MAY** in this document are to be interpreted as described in
[RFC 2119](https://datatracker.ietf.org/doc/html/rfc2119) and
[RFC 8174](https://datatracker.ietf.org/doc/html/rfc8174).

- **Provider** — the operator of an x402-paid HTTP service (the
  *resource server* in x402 vocabulary).
- **Agent** — the paying client (a long-running automation, an LLM
  agent, or a script).
- **Facilitator** — the settlement intermediary that verifies and
  settles the EIP-712 PAYMENT-SIGNATURE on chain.
- **Settlement** — the on-chain transfer of value triggered by a valid
  PAYMENT-SIGNATURE. One PAYMENT-SIGNATURE produces one Settlement.
- **Payment** — the unit of money. One Settlement creates exactly one
  Payment, identified by `paymentId`. A Payment is the natural object
  against which refund operations are reconciled: a single Payment
  may have one or more refund operations (full, partial, or
  per-Order), and the sum of refunded + kept atomic units MUST
  equal the original Payment amount.
- **Order** — a unit of fulfillment work the provider performs after a
  Payment, identified by `orderId`. One Payment MAY produce one or
  more Orders. The simple "one Payment, one Order" case covers most
  endpoints; carts, bundle vouchers, multi-SKU purchases, and
  multi-leg topups produce multiple Orders against a single Payment.
- **Line item** — sub-unit of an Order, used when an Order contains
  multiple deliverables and they may succeed or fail independently
  (e.g. a 3-pack voucher bundle where one voucher fails to mint).
  Optional concept for v0.1; providers without bundles MAY ignore it.
- **Fulfillment** — the act of producing the goods or data the agent
  paid for (an eSIM QR code, an API answer, a topup credit, etc.). A
  single Order may have one or many Fulfillments depending on Line
  items.
- **Compensating action** — an alternate delivery (re-issue, substitute
  good) accepted in lieu of a refund. Always optional.

> **Why this matters.** Earlier drafts conflated Payment with Order.
> The split lets the spec describe partial refunds (Payment refunded
> in part because one Line item of an Order failed), bundle products
> (one Payment, multiple Orders, fulfilled independently), and
> recovery flows (when the original `200` response is lost, the agent
> still has a `paymentId` to resume from).

## 3. State machine

### 3.1 Canonical lifecycle

```
                 ┌──────────────────────────────────────────────┐
BEFORE PAYMENT:  │ AVAILABLE / TEMPORARILY_UNAVAILABLE / RISKY / │
                 │ NOT_SUPPORTED                                 │
                 └──────────────────────────────────────────────┘
                                    │
                              (agent pays)
                                    │
                                    ▼
                              PAID  (paymentId issued)
                                    │
                              (one or more Orders created)
                                    │
                ┌───────────────────┼───────────────────────────┐
                │                                                │
                ▼                                                ▼
       FULFILLING (per Order)                                EXPIRED
                │                                                │
       ┌────────┴───────────┐                                    │
       ▼                    ▼                                    │
   FULFILLED         FULFILLMENT_FAILED                           │
   (terminal:               │                                     │
     success)               ▼                                     │
                  ┌────────────────────────┐                      │
                  │   refund_policy.type   │◄─────────────────────┘
                  │  ───────────────────── │
                  │ automatic │  manual    │
                  └─────┬─────┴────┬───────┘
                        │          │
            ┌───────────┘          ▼
            │              REFUND_AVAILABLE
            │              (agent_action: claim_refund;
            │               agent must POST refund_endpoint)
            │                      │
            │           (agent claims; idempotent)
            │                      │
            ▼                      ▼
       REFUND_PENDING ◄───────────┘
            │
            ├───────────────────┬─────────────────────┐
            ▼                   ▼                     ▼
       REFUNDED          PARTIALLY_REFUNDED      REFUND_FAILED
       (terminal:        (terminal:              (terminal:
        full refund       partial refund —        needs human)
        completed)        e.g. one Line item
                          paid out, one not)
```

The Order branches and the refund branches are independent state
machines that share the `paymentId`. A single Payment may have several
Orders in different fulfillment states simultaneously; the
Payment-level refund state is computed from them according to the
provider's `refund_policy`.

### 3.2 Pre-payment states

| State | Meaning | Agent response |
|---|---|---|
| `AVAILABLE` | Service is healthy and accepting orders. | Pay. |
| `TEMPORARILY_UNAVAILABLE` | Provider is up but a dependency is down. Retry later. | Wait, then retry. |
| `RISKY` | Service is up but elevated failure risk (e.g. upstream slow). Agent SHOULD apply higher confidence threshold or back off. | Optional pay. |
| `NOT_SUPPORTED` | Order would not be fulfillable (out of stock, SKU retired). | Do not pay. |

These map to the `signals.provider_health` + `signals.agent_action`
fields in §4.3.

### 3.3 Post-payment states

Order-level states (apply per Order):

| State | Meaning |
|---|---|
| `PAID` | Settlement on chain confirmed. One or more Orders created against the Payment. |
| `FULFILLING` | Provider is actively producing the deliverable for this Order. |
| `FULFILLED` | **Terminal success.** Deliverable handed off to agent (synchronously in response, or via the status endpoint). |
| `FULFILLMENT_FAILED` | Provider determined fulfillment of this Order is not possible (upstream timeout, SKU now unavailable, etc.). Triggers refund flow per `refund_policy`. |
| `EXPIRED` | Order exceeded `fulfillment_policy.fulfillment_deadline_seconds` without reaching FULFILLED or FULFILLMENT_FAILED. Equivalent to FULFILLMENT_FAILED for refund purposes. |

Refund-level states (apply per Payment):

| State | Meaning |
|---|---|
| `REFUND_AVAILABLE` | One or more Orders failed and the provider's `refund_policy.type = "manual"`. The agent MUST POST `refund_endpoint` to claim a refund (and SHOULD do so within `refund_policy.refund_claim_deadline_seconds`, if declared). The transition target after a successful claim is `REFUND_PENDING`. |
| `REFUND_PENDING` | A refund has been accepted by the provider (either automatically via `triggers`, or because the agent claimed it). The on-chain transfer back to the original payer is in flight. The provider SHOULD complete it within `refund_policy.refund_deadline_seconds`. |
| `REFUNDED` | **Terminal success (negative).** The full settled amount has been returned to the original payer. |
| `PARTIALLY_REFUNDED` | **Terminal success (negative, partial).** Less than the full settled amount was returned. Used when only some Line items of an Order failed (the remainder was kept for the items actually delivered) or when an overcharge is corrected. The refund object MUST report `amount_atomic_refunded` and `amount_atomic_kept` so the agent can reconcile. |
| `REFUND_FAILED` | **Terminal failure.** The provider cannot or will not refund. Operator intervention required. The agent SHOULD log this and move the Payment to a human-review queue. |

### 3.4 Why explicit terminals matter

`DONE` is a tempting terminal but ambiguous (cf. Google
[Long Running Operations](https://cloud.google.com/apis/design/design_patterns#long_running_operations)
where `done: true` can mean success **or** error and downstream
consumers must inspect a separate `result.error` field). x402-signals
v0.1 separates the terminal vocabulary (`FULFILLED` /
`FULFILLMENT_FAILED` / `REFUNDED` / `PARTIALLY_REFUNDED` /
`REFUND_FAILED`) so an agent can branch on the status string alone
without parsing a result envelope.

This mirrors the explicit terminals in
[Stripe Refunds](https://docs.stripe.com/api/refunds/object)
(`succeeded` / `failed` / `canceled`),
[Adyen Refunds](https://docs.adyen.com/online-payments/refund/),
[Mollie Refunds](https://docs.mollie.com/reference/v2/refunds-api/get-refund),
and
[Coinbase Commerce refund_status](https://docs.cdp.coinbase.com/commerce/docs).

### 3.5 Manual vs automatic refund flow

The state machine path from `FULFILLMENT_FAILED` to `REFUND_PENDING`
differs by `refund_policy.type`:

- **`automatic`** — provider self-triggers refund. Transition is
  direct: `FULFILLMENT_FAILED → REFUND_PENDING`. The agent does not
  need to call `refund_endpoint`; it MAY poll the Payment status to
  observe the transition.
- **`manual`** — the Payment enters `REFUND_AVAILABLE`. The agent
  observes `agent_action: "claim_refund"` and MUST POST
  `refund_endpoint` (with `Idempotency-Key`) to advance to
  `REFUND_PENDING`. If the agent never claims, the Payment remains in
  `REFUND_AVAILABLE` until the provider's claim deadline expires (then
  the provider MAY archive it). v0.1 does not normalise the archival
  semantics; future versions may.
- **`none`** — there is no refund flow. The Payment terminates at the
  Order-level `FULFILLMENT_FAILED` and remains there. Agents reading
  `refund_policy.type = "none"` SHOULD avoid paying providers that
  return this in critical paths.

## 4. The three buckets

A provider that implements x402-signals v0.1 publishes (some of) three
top-level fields in its `/.well-known/x402` document:

```json
{
  "fulfillment_policy": { ... },
  "refund_policy":      { ... },
  "signals":            { ... }
}
```

Providers MAY publish any subset; missing fields are treated as
"unspecified" (see §4.4 for default behaviour).

### 4.1 `fulfillment_policy`

Describes when the goods are delivered, how long the agent should
expect to wait, and how to recover the deliverable if the original
HTTP response is lost.

```json
{
  "fulfillment_policy": {
    "mode": "instant",
    "fulfillment_deadline_seconds": 60,
    "status_endpoint": "/api/orders/{orderId}",
    "retry_after_seconds": 5
  }
}
```

```json
{
  "fulfillment_policy": {
    "mode": "async",
    "fulfillment_deadline_seconds": 86400,
    "status_endpoint": "/api/orders/{orderId}",
    "retry_after_seconds": 60
  }
}
```

| Field | Type | Required | Meaning |
|---|---|---|---|
| `mode` | `"instant" \| "async"` | yes | `instant`: deliverable is intended to be returned synchronously in the 200 response body. `async`: 200 response carries `paymentId` + at least one `orderId` and no deliverable; agent polls `status_endpoint`. **Both modes** require the response to include `paymentId` and `orderId` so that lost responses can be recovered (see §4.1.1). |
| `fulfillment_deadline_seconds` | integer ≥ 1 | yes | Maximum time from `PAID` to **a terminal fulfillment state** (`FULFILLED` / `FULFILLMENT_FAILED` / `EXPIRED`). After this, any Order still in `FULFILLING` MUST transition to `EXPIRED`. This is **separate from the refund deadline** in §4.2 — `EXPIRED` only triggers the refund flow; the refund itself has its own clock. |
| `status_endpoint` | URL template | yes (both modes) | Where the agent polls for current state. The provider MUST accept `{orderId}` (preferred) or `{paymentId}` substitution. In `instant` mode, this is a recovery path: the agent calls it only if the original response was lost or never received. |
| `retry_after_seconds` | integer ≥ 1 | yes (both modes) | Suggested poll interval. Mirrors HTTP [`Retry-After`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Retry-After) semantics. For `instant` mode, the agent SHOULD wait at least one such interval before falling back to the status endpoint. |

#### 4.1.1 Lost-response recovery

The 200 response body to a paid call MUST include both `paymentId` and
at least one `orderId` regardless of `mode`:

```json
{
  "paymentId": "pay_01H8...",
  "orders": [
    { "orderId": "ord_01H8a...", "state": "FULFILLED", "result": { ... } }
  ]
}
```

Rationale: settlement happens on chain before the provider returns its
response. If the connection is interrupted between the provider's
`200` write and the agent receiving it, the agent has paid and has no
key to look up what happened. The minimum recovery primitive is for
the response to carry **identifiers the agent can replay against the
status endpoint**, even in `instant` mode.

If the agent times out on the `200` it MAY:

1. Use the on-chain `transactionHash` (recoverable from the
   facilitator's PAYMENT-RESPONSE or directly from the wallet's
   transaction history) to call status lookup —
   `status_endpoint?transactionHash=...`. The provider MUST support
   `transactionHash` lookup and SHOULD return the same response shape
   it would have returned to the original POST, including the
   provider-internal `paymentId`. The agent does **not** derive
   `paymentId` from the hash — `paymentId` is provider-internal and
   only the provider can map a hash to it.
2. Replay the original PAYMENT-SIGNATURE. The provider MUST treat this
   as idempotent — same Payment, same Order(s), same deliverables,
   no second on-chain settlement.

#### 4.1.2 Note on `mode = "instant"`

If the deliverable is large or the upstream supplier may briefly take
more than the HTTP timeout, the provider SHOULD declare
`mode = "async"` and return immediately with `paymentId + orderId` and
no deliverable, even if the typical fulfillment time is sub-second.
This is the same trade-off the
[Microsoft REST API guidelines](https://learn.microsoft.com/en-us/azure/architecture/patterns/async-request-reply)
recommend (`202 Accepted` + `Location` for long-running work).

### 4.2 `refund_policy`

Describes when, where, and how money returns to the original payer.
The refund clock is **separate** from the fulfillment clock (§4.1):
fulfillment may fail in seconds, but the on-chain refund itself takes
its own time.

```json
{
  "refund_policy": {
    "type": "automatic",
    "triggers": ["fulfillment_failed", "expired", "upstream_timeout"],
    "refund_to": "original_payer",
    "refund_endpoint": "/api/refunds/{paymentId}",
    "refund_deadline_seconds": 86400,
    "refund_claim_deadline_seconds": null,
    "partial_refunds_supported": true,
    "idempotency_required": true,
    "compensating_actions_optional": true
  }
}
```

| Field | Type | Required | Meaning |
|---|---|---|---|
| `type` | `"automatic" \| "manual" \| "none"` | yes | `automatic`: refund executes without agent action. `manual`: agent MUST POST the `refund_endpoint` to claim a refund (Payment enters `REFUND_AVAILABLE`). `none`: provider does not refund (agent SHOULD treat the order as buy-only). |
| `triggers` | array of strings | required if `type = automatic` | Conditions that produce an automatic refund. Reserved values: `fulfillment_failed`, `expired`, `upstream_timeout`, `payment_overcharge`, `partial_fulfillment_failure`. Operators MAY add custom strings; consumers MUST ignore unknown values. |
| `refund_to` | `"original_payer" \| string` | yes | Address that receives the refund. `"original_payer"` resolves to the payer recovered from the original PAYMENT-SIGNATURE. |
| `refund_endpoint` | URL template | required if `type = manual`, or whenever a refund status / lookup endpoint is offered (recommended for `automatic` too) | Used for claiming a manual refund (`POST`) and for fetching the state of an existing refund (`GET`). |
| `refund_deadline_seconds` | integer ≥ 1 | yes if `type ≠ none` | Maximum time from refund acceptance (`REFUND_PENDING`) to a terminal refund state (`REFUNDED` / `PARTIALLY_REFUNDED` / `REFUND_FAILED`). This is the on-chain SLA the provider commits to. Independent of `fulfillment_deadline_seconds`. |
| `refund_claim_deadline_seconds` | integer ≥ 1 \| `null` | optional, `type = manual` only | If non-null, agents have at most this many seconds from `REFUND_AVAILABLE` to POST `refund_endpoint`. Past this deadline the provider MAY refuse to refund. `null` means no deadline. |
| `partial_refunds_supported` | boolean | yes if `type ≠ none` | If `true`, the provider MAY return less than the full settled amount when only some Line items / Orders failed. If `false`, the provider always refunds in full or not at all (Order with one failed Line item refunds the whole Payment). |
| `idempotency_required` | boolean | yes | If `true`, the agent MUST include an `Idempotency-Key` header on every POST to `refund_endpoint`. The key MUST be unique per logical refund claim and MUST be reused on retries (see §7.3). |
| `compensating_actions_optional` | boolean | yes | If `true`, the provider MAY offer the agent a substitute deliverable (re-issue, equivalent SKU) instead of money. The agent retains the right to reject and demand cash refund per `refund_policy.type`. |

**`refund_to`.** `"original_payer"` is the default and is satisfiable
purely from the PAYMENT-SIGNATURE the agent already submitted — no
extra discovery step needed. Static addresses are allowed but
discouraged: an agent that pays from a hot wallet may have rotated keys
by the time a refund fires.

**Partial refunds.** When `partial_refunds_supported = true` and only
some Orders / Line items of a Payment fail, the provider MAY emit a
`PARTIALLY_REFUNDED` terminal. The refund object MUST then carry
`amount_atomic_refunded` and `amount_atomic_kept` so the agent can
reconcile its books without parsing free-form `reason` strings.
`payment_overcharge` triggers (catalog list price differs from the
amount in the 402 challenge) naturally produce partial refunds:
provider keeps the catalog price, refunds the delta.

### 4.3 `signals`

Live operational state. SHOULD be served on a fast-path so the agent
can read it before paying.

```json
{
  "signals": {
    "provider_health": "healthy",
    "agent_action": "pay",
    "last_updated": "2026-05-08T14:30:00Z"
  }
}
```

| Field | Type | Required | Meaning |
|---|---|---|---|
| `provider_health` | `"healthy" \| "degraded" \| "down"` | yes | Aggregate self-report. `degraded` SHOULD widen agent timeouts; `down` SHOULD short-circuit the call. |
| `agent_action` | `"pay" \| "retry_later" \| "wait" \| "claim_refund" \| "stop"` | yes | Recommended action for an agent inspecting this field right now. `claim_refund` only appears in a status-endpoint response, not in `/.well-known/x402`. |
| `last_updated` | ISO 8601 timestamp | yes | When this signal was last refreshed. Stale signals (`now - last_updated > 5m` is a reasonable cutoff) MUST be treated by the agent as `provider_health: "down"`. |

`agent_action` mappings:

- `pay` — provider is healthy. Proceed with x402 payment.
- `retry_later` — provider is degraded. Agent SHOULD back off and retry
  (suggested: at least one minute) before paying.
- `wait` — an existing async Order is in flight. Used in the response
  body of a `status_endpoint`, not in `/.well-known/x402`.
- `claim_refund` — used in a status response when the Payment is in
  `REFUND_AVAILABLE` and `refund_policy.type = "manual"`. The agent
  MUST POST `refund_endpoint` (with `Idempotency-Key`) to advance.
- `stop` — provider is down or refusing new orders. Agent MUST NOT pay.

### 4.4 Behaviour when a bucket is missing

When a bucket is absent, an agent MUST pick a default. v0.1 defines
two default postures, and agents SHOULD declare to themselves which
they use:

- **Legacy-compatible default** (preserves the pre-spec status quo):
  - Missing `fulfillment_policy` → assume `mode = "instant"`,
    `fulfillment_deadline_seconds = 60`. If the response is not
    received within 60 seconds, treat as `EXPIRED`.
  - Missing `refund_policy` → assume `type = "none"`.
  - Missing `signals` → assume `provider_health = "healthy"`,
    `agent_action = "pay"`.
- **Safety-conservative default** (recommended for high-value or
  irreversible payments):
  - Missing `fulfillment_policy` → still assume `mode = "instant"`,
    `fulfillment_deadline_seconds = 60`, but require external pre-flight.
  - Missing `refund_policy` → assume `type = "none"` AND **refuse to
    pay** unless explicitly opted in for the specific provider.
  - Missing `signals` → assume `provider_health = "unknown"`,
    `agent_action = "stop"` (caller must opt in to pay).

The legacy-compatible default is named explicitly so it isn't
mis-described as "conservative" — it is in fact optimistic, biased
toward interoperability with providers that pre-date this spec. Agents
that need stronger guarantees (treasury operations, large one-shot
payments, irreversible commitments) SHOULD use the safety-conservative
default and / or layer an external safety oracle on top.

## 5. Wire format

### 5.1 Where the document lives

A provider MAY publish either or both of the following. When both are
present, the **challenge extension wins** for that specific 402
response (per-route override); the `/.well-known/x402` form is the
global default.

1. **`/.well-known/x402` field.** The three buckets sit at the top
   level of the existing `.well-known/x402` JSON document, alongside
   `endpoints`, `name`, etc.

   ```json
   {
     "x402Version": 2,
     "name": "ExampleService",
     "endpoints": [ ... ],
     "fulfillment_policy": { ... },
     "refund_policy": { ... },
     "signals": { ... }
   }
   ```

2. **x402 challenge extension.** When a provider returns a 402
   challenge, it MAY include the buckets in the
   `extensions["x402-signals"]` field of the PAYMENT-REQUIRED body.
   The challenge body has top-level `accepts` (an array of accepted
   payment options); the extension nests under each accepted entry's
   `extensions` object:

   ```json
   {
     "x402Version": 2,
     "error": "Payment required",
     "resource": { ... },
     "accepts": [ {
       "scheme": "exact",
       "network": "eip155:8453",
       "amount": "1000",
       "asset": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
       "payTo": "0x4053338C7cB38624C0bc23c900F78Cf8470b4E38",
       "maxTimeoutSeconds": 300,
       "extra": { "name": "USD Coin", "version": "2" },
       "extensions": {
         "x402-signals": {
           "fulfillment_policy": { ... },
           "refund_policy": { ... },
           "signals": { ... }
         }
       }
     } ]
   }
   ```

   Per-route signals (a single endpoint may have a different policy
   from the rest of the service) belong in this extension. The field
   names `accepts`, `x402Version`, `extensions` are taken from the
   x402 v2 challenge envelope as observed in the published x402 SDKs
   (`@x402/core`, `@x402/next`).

### 5.2 Versioning

The buckets MAY carry a sibling `version` field:

```json
{
  "fulfillment_policy": { "version": "0.1", "mode": "instant", ... }
}
```

Agents MUST accept any value of `version` they recognise; unknown
versions SHOULD be treated as if the bucket is missing.

The intent is to allow non-breaking evolution: v0.2 may add fields,
must not redefine v0.1 fields.

## 6. Status endpoint contract

The status endpoint exists in **both** `instant` and `async` modes:

- In `async` mode it is the primary delivery channel — the agent
  polls it after the initial 200 to learn when the deliverable is
  ready.
- In `instant` mode it is a recovery channel — the agent calls it
  only if the original 200 response was lost.

### 6.1 Request

The status endpoint accepts lookup by `orderId` (preferred) or
`paymentId`:

```
GET /api/orders/{orderId}
GET /api/orders?paymentId={paymentId}
GET /api/orders?transactionHash={onChainTxHash}
Authorization: <agent-bearer-or-original-payment-signature-replay>
```

The provider MAY require the agent to replay the PAYMENT-SIGNATURE
header, or issue a short-lived bearer token in the original
fulfillment response. v0.1 does not normalise the auth method; future
versions may. Providers SHOULD support `transactionHash` lookup so an
agent can recover from a lost 200 even when it never received the
provider's `paymentId`.

### 6.2 Response

The response describes a Payment plus its Orders. Single-Order
responses are the common case; carts / bundles return multiple Orders.

```json
{
  "paymentId": "pay_01H8...",
  "transactionHash": "0xdeae...622a8",
  "orders": [
    {
      "orderId": "ord_01H8a...",
      "state": "FULFILLING",
      "state_updated_at": "2026-05-08T14:30:42Z",
      "fulfillment_deadline": "2026-05-09T14:30:00Z",
      "agent_action": "wait",
      "result": null,
      "error": null
    }
  ],
  "refund_state": null
}
```

When all Orders are `FULFILLED`:

```json
{
  "paymentId": "pay_01H8...",
  "transactionHash": "0xdeae...622a8",
  "orders": [
    {
      "orderId": "ord_01H8a...",
      "state": "FULFILLED",
      "state_updated_at": "2026-05-08T14:31:08Z",
      "agent_action": null,
      "result": { "iccid": "8943...", "qr_url": "https://..." },
      "error": null
    }
  ],
  "refund_state": null
}
```

When at least one Order has failed and `refund_policy.type = "manual"`:

```json
{
  "paymentId": "pay_01H8...",
  "transactionHash": "0xdeae...622a8",
  "orders": [
    {
      "orderId": "ord_01H8a...",
      "state": "FULFILLMENT_FAILED",
      "state_updated_at": "2026-05-08T14:31:08Z",
      "agent_action": "claim_refund",
      "result": null,
      "error": { "code": "upstream_timeout", "message": "Carrier ack timeout" }
    }
  ],
  "refund_state": "REFUND_AVAILABLE"
}
```

Order-level `state` MUST be one of the Order-level post-payment states
in §3.3. `agent_action` is informational and may be null when no
further action is needed.

### 6.3 Status response when refund is in flight

`refund_state` is the Payment-level refund state (§3.3): one of
`null` (no refund flow active), `REFUND_AVAILABLE`, `REFUND_PENDING`,
`REFUNDED`, `PARTIALLY_REFUNDED`, `REFUND_FAILED`. Agents that don't
understand the field MAY ignore it; agents that do can avoid firing a
duplicate refund claim or know when an automatic refund is in flight.

## 7. Refund endpoint contract

### 7.1 Request

```
POST /api/refunds
Idempotency-Key: <agent-controlled-uuid-or-similar>
Authorization: <agent-bearer-or-original-payment-signature>

{
  "paymentId": "pay_01H8...",
  "reason": "client_did_not_receive_goods"
}
```

`paymentId` is the provider's own reference for the original Payment.
A provider that does not maintain a payment ID MAY accept the
on-chain `transactionHash` instead. Providers SHOULD accept either.
Agents claiming a partial refund MAY include an optional `orderIds`
array to narrow the scope:

```json
{
  "paymentId": "pay_01H8...",
  "orderIds": ["ord_01H8b..."],
  "reason": "one_voucher_of_three_failed"
}
```

### 7.2 Response

A successful refund creation or status fetch returns a 2xx with the
refund object. Errors use ordinary HTTP semantics
(`400`, `404`, `409 Conflict` for an idempotency-key collision against
a different request body, `429`, `5xx`, etc.). For long-running on-chain
refunds the provider MAY return `202 Accepted` with a `Location`
header pointing at the refund object — agents follow `Location`.

```json
{
  "refundId": "ref_01H8...",
  "paymentId": "pay_01H8...",
  "state": "REFUND_PENDING",
  "state_updated_at": "2026-05-08T14:31:09Z",
  "refund_to": "0x30d2b1f9bcEdE5F13136b56Ff199A8ad6E4f50de",
  "amount_atomic": "2590000",
  "amount_atomic_refunded": null,
  "amount_atomic_kept": null,
  "asset": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
  "asset_decimals": 6,
  "network": "eip155:8453",
  "transactionHash": null,
  "reason": "client_did_not_receive_goods",
  "idempotency_key": "9c2f...",
  "deadline": "2026-05-09T14:31:09Z"
}
```

Field semantics:

- `state` MUST be one of `REFUND_PENDING`, `REFUNDED`,
  `PARTIALLY_REFUNDED`, `REFUND_FAILED`.
- `amount_atomic` is the atomic-unit representation of the original
  Payment amount (decimal string, never JSON number — JSON numbers
  lose precision past 2^53). For USDC on Base, atomic units are
  6-decimal: $2.59 = `"2590000"`.
- `asset` is the on-chain asset identifier. For EVM networks this is
  the ERC-20 contract address; non-EVM networks SHOULD use a
  [CAIP-19](https://chainagnostic.org/CAIPs/caip-19) `assetId` string.
- `asset_decimals` is the asset's decimal scale (6 for USDC, 18 for
  ETH). Always declared so consumers don't have to look it up.
- `amount_atomic_refunded` and `amount_atomic_kept` SHOULD be `null`
  while `state = REFUND_PENDING` and MUST be populated on terminal
  states. For full refunds:
  `amount_atomic_refunded = amount_atomic, amount_atomic_kept = "0"`.
  For partial refunds: both non-zero, summing to `amount_atomic`.
- `deadline` is the provider's commitment for transitioning to a
  terminal refund state, derived from
  `refund_policy.refund_deadline_seconds`.

Decimal-string display amounts (`"2.59"`, `"USDC"`) are display hints,
not canonical accounting. Always reconcile against
`(amount_atomic, asset, asset_decimals)`.

### 7.3 Idempotency requirement

If `refund_policy.idempotency_required = true`, the provider:

- MUST require an `Idempotency-Key` HTTP header on every POST to
  `refund_endpoint`.
- MUST treat repeated requests with the same `(paymentId, Idempotency-Key)`
  as the same logical refund claim — same `refundId`, same response
  body. Retrying a network-failed POST with the **same** key and the
  **same** body is the canonical recovery path; sending a **new** key
  on retry creates a duplicate claim and defeats the purpose of
  idempotency.
- MUST persist the `(paymentId, Idempotency-Key)` mapping for at
  least 24 hours so retries within that window remain idempotent.
- MAY return `409 Conflict` when the same key is reused with a
  different request body (a programming error on the agent side).

The agent's contract:

- The `Idempotency-Key` MUST be unique per **logical refund claim**
  (one claim per Payment / orderIds tuple in v0.1).
- All retries of the same logical claim MUST reuse the same key.
- A new claim (e.g. for a different Payment) MUST use a fresh key.

This matches Stripe's
[idempotent requests](https://docs.stripe.com/api/idempotent_requests)
and Coinbase's `x-idempotency-key` requirement.

### 7.4 Polling for refund completion

Agents poll `GET /api/refunds/{refundId}` (or follow `Location` from
a 202 response) until the refund reaches a terminal state. The agent
SHOULD poll at most every `retry_after_seconds` (if declared) or
every 30 seconds otherwise. Long-poll variants MAY be supported by the
provider but are not required by v0.1.

## 8. Reference example — eSIM purchase

The example below is **illustrative**: it shows how an x402-signals
v0.1 manifest, status response, and refund object would look for
ReloadPI's eSIM API. The on-chain payment (`#XPAY1`) is real; the
spec-conformant manifest, status endpoint, and refund endpoint are
what this draft is asking ReloadPI (and other operators) to publish.

### 8.1 Manifest as proposed

```json
// GET https://api.reloadpi.com/.well-known/x402
{
  "x402Version": 2,
  "name": "Reloadpi",
  "endpoints": [ ... ],
  "fulfillment_policy": {
    "mode": "instant",
    "fulfillment_deadline_seconds": 60,
    "status_endpoint": "/api/orders/{orderId}",
    "retry_after_seconds": 5
  },
  "refund_policy": {
    "type": "automatic",
    "triggers": ["fulfillment_failed", "upstream_timeout"],
    "refund_to": "original_payer",
    "refund_endpoint": "/api/refunds",
    "refund_deadline_seconds": 86400,
    "refund_claim_deadline_seconds": null,
    "partial_refunds_supported": true,
    "idempotency_required": true,
    "compensating_actions_optional": true
  },
  "signals": {
    "provider_health": "healthy",
    "agent_action": "pay",
    "last_updated": "2026-05-08T14:25:00Z"
  }
}
```

### 8.2 Happy path (real payment, illustrative response shape)

1. Agent reads `/.well-known/x402`. `signals.agent_action = "pay"`.
2. Agent `POST /api/catalog/esims/purchase` with
   `{offerId: "ESIM-GB-1D-UNLIMITED-NOROAM"}`. Provider returns
   `402 Payment Required`; the `payment-required` header carries the
   v2 challenge.
3. Agent signs the EIP-712 PAYMENT-SIGNATURE, retries the POST.
4. Facilitator settles on Base mainnet
   (block 45,728,213, tx
   [`0xdeae...622a8`](https://basescan.org/tx/0xdeaed418b8b052da65969d9c299d341681bfc314cb6731344d7d4d3fac0622a8),
   2,590,000 atomic USDC = $2.59).
5. Provider returns `200`. Under v0.1 the body would be:

   ```json
   {
     "paymentId": "pay_01H8...",
     "transactionHash": "0xdeae...622a8",
     "orders": [
       {
         "orderId": "ord_01H8a...",
         "state": "FULFILLED",
         "state_updated_at": "2026-05-08T14:30:55Z",
         "result": {
           "iccid": "8943108167002078039",
           "qr_url": "https://...",
           "activation_code": "..."
         },
         "error": null
       }
     ],
     "refund_state": null
   }
   ```

   End-to-end wall clock: 13.5 seconds.
6. If the agent's HTTP client times out before receiving step 5, it
   recovers via
   `GET /api/orders?transactionHash=0xdeae...622a8` and reads the
   same `result` object.

### 8.3 Failure path (illustrative)

If the carrier API had timed out, the same call would have returned
`200` with body:

```json
{
  "paymentId": "pay_01H8...",
  "transactionHash": "0xdeae...622a8",
  "orders": [
    {
      "orderId": "ord_01H8a...",
      "state": "FULFILLMENT_FAILED",
      "state_updated_at": "2026-05-08T14:30:55Z",
      "result": null,
      "error": { "code": "upstream_timeout", "message": "Carrier ack timeout" }
    }
  ],
  "refund_state": "REFUND_PENDING"
}
```

Because `refund_policy.type = "automatic"`, the agent does not need to
call `refund_endpoint`. The provider commits to transitioning the
Payment to `REFUNDED` (full) within `refund_deadline_seconds = 86400`.
The agent MAY poll `GET /api/refunds?paymentId=pay_01H8...` to watch
progress.

### 8.4 Partial-refund path (illustrative — multi-leg topup)

Imagine a Payment for a $5 topup bundle covering three leg-mints, two
of which succeed:

```json
{
  "refundId": "ref_01H8c...",
  "paymentId": "pay_01H8c...",
  "state": "PARTIALLY_REFUNDED",
  "state_updated_at": "2026-05-08T14:35:00Z",
  "refund_to": "0x30d2b1f9bcEdE5F13136b56Ff199A8ad6E4f50de",
  "amount_atomic": "5000000",
  "amount_atomic_refunded": "1666666",
  "amount_atomic_kept": "3333334",
  "asset": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
  "asset_decimals": 6,
  "network": "eip155:8453",
  "transactionHash": "0x...",
  "reason": "partial_fulfillment_failure",
  "deadline": "2026-05-09T14:30:00Z"
}
```

The agent reconciles `1666666 / 10^6 = $1.67` returned for the failed
leg, `3333334 / 10^6 = $3.33` retained for the two successful legs.

## 9. Security considerations

### 9.1 Replay of the refund endpoint

If `refund_to` is `"original_payer"` (the default), the provider MUST
re-derive the payer address from the original PAYMENT-SIGNATURE
recovered EIP-712 signer rather than from any agent-supplied value.
Otherwise an attacker who learned a `paymentId` could redirect refunds.

### 9.2 Trust in `signals`

`signals` is a self-report. Agents MUST NOT treat
`signals.provider_health = "healthy"` as proof of liveness. A safety
oracle (e.g. an external pre-flight service such as
[x402station.io](https://x402station.io)) SHOULD be consulted by
high-stakes agents. `x402-signals` covers what the provider declares;
external oracles cover what the provider actually does.

### 9.3 Refund draining

`refund_policy.type = "manual"` with no `idempotency_required`
field is an attractive nuisance: a malicious party that learned a
`paymentId` could issue duplicate refund POSTs. Providers SHOULD
require `idempotency_required = true` whenever `type = "manual"`.
Providers SHOULD also bind the refund target to the original payer
(`refund_to: "original_payer"`) so a leaked `paymentId` cannot be
used to redirect funds — see §9.1.

### 9.4 Stale `signals.last_updated`

A provider that returns `provider_health: "healthy"` but
`last_updated` from yesterday is signalling broken health-check
machinery. Agents SHOULD treat freshness > 5 minutes as
`provider_health: "down"`.

### 9.5 Front-running fulfillment

This document does not address front-running of unique digital goods
(NFT mints, scarce SKUs). x402-signals is a fulfillment / refund
convention, not an MEV mitigation. Operators of scarce-goods endpoints
SHOULD use other mechanisms (commit-reveal, allowlists) layered on top.

### 9.6 Loss of the `200` response

The `200` body to a paid call carries the deliverable in `instant`
mode. If the connection is interrupted between the provider's
`200` write and the agent receiving it, the agent has paid, the
provider believes the order was fulfilled, and the deliverable is
lost. Spec compliance with §4.1.1 (mandatory `paymentId` + `orderId`
in every paid response) and §6 (status endpoint accepting
`transactionHash` lookup) is what makes this recoverable. Providers
that omit the status endpoint or the identifiers SHOULD be flagged
by external safety oracles as **incomplete** even if they otherwise
publish a manifest.

## 10. Compatibility and migration

### 10.1 Providers that do not implement x402-signals

x402 services without `fulfillment_policy` / `refund_policy` /
`signals` continue to function. Agents that see no signals fall back to
their previous heuristic behaviour. Pre-flight oracles MAY flag absence
as a non-fatal warning but MUST NOT block payment on absence alone.

### 10.2 Agents that do not implement x402-signals

Agents that ignore the three buckets continue to interoperate with
v0.1-implementing providers exactly as they did before. The new fields
are additive.

### 10.3 Future versions

v0.2 may:

- Add a registered set of refund reason codes.
- Add a normative auth method for status / refund endpoints.
- Add per-bucket `version` semantics for negotiation.
- Add observability hooks (Prometheus / OpenTelemetry attribute names).

v0.2 MUST NOT redefine any v0.1 field name with new semantics. Field
deprecations require a major-version bump.
